# Connection Registry Design: Consolidated Corrections Report

> This is a pre-implementation red-team critique of `connection-registry-design.md`, not a
> description of shipped behavior; the as-built connections model has since diverged from both
> documents. For the current, code-verified behavior see
> [docs/reference/concepts/connections-and-secrets.md](reference/concepts/connections-and-secrets.md)
> and [docs/reference/flow/connections.md](reference/flow/connections.md).

Target document: `C:\Projects\SQLFlowV3\docs\connection-registry-design.md`

## 1. Headline

The design is architecturally sound in its core shape (one `ConnectionRef`, one resolver, one factory as the sole open site, capabilities riding into providers, secretless-at-rest, two-modes-one-engine) and most of it survives the red team. It is NOT yet safe to build as written. Three classes of blocking defects must be corrected first: (a) the no-resting-secret enforcement is bypassable by whitespace and is logically contradictory for two AAD modes, so it does not actually deliver architecture goal 7; (b) the "single open site / Single Code Path" claim is false because a second connection-resolution-and-open path (`InferenceService`) is entirely absent from the impact analysis, and the source-by-alias story (`ConnectionRole.Source`, `SourceSpec.Location`, the `type: ado` example) is presented as working when no relational reader exists and nothing resolves a source connection; and (c) the migration mapping (section 5.3) contains several factual errors about the legacy schema and is not column-complete. Section 10 decision 1 (wire MySQL now, return `DbConnection`) resolves part of the layering objection but introduces a new, unaddressed provider-downcast problem. Fix the blocking items below, then build.

## 2. Confirmed HIGH-severity corrections (blocking)

### H1. No-resting-secret guards are bypassable by whitespace (sections 1.4 and 5.1)
Problem: Both the section 1.4 inline validation and the section 5.1 `CK_DataSource_NoRestingSecret` CHECK (`ConnectionRef NOT LIKE '%password=%' AND ... '%pwd=%'`) match raw text for the literal substring `password=`. `Microsoft.Data.SqlClient` (V3 pins 6.0.2, verified in `C:\Projects\SQLFlowV3\Directory.Packages.props` line 9) tolerates whitespace around `=`, so `Password =Hunter2` and `Pwd\t= Hunter2` parse into a live password but defeat the substring check. The "enforceable, not aspirational" (1.4) and "write-time failure" (5.1) claims are false.
Fix: Do not substring-match raw text. Validate after canonicalizing through `SqlConnectionStringBuilder`: build it, then reject if `!string.IsNullOrEmpty(b.Password)` (the builder normalizes `Password`/`Pwd`/`PWD` and whitespace variants to one non-empty `Password` property). Make the SQL CHECK defense-in-depth only, store only the already-canonicalized `ConnectionRef`, and make the constraint whitespace- and collation-tolerant, e.g. `CHECK (ConnectionRef LIKE '${%}' OR (REPLACE(LOWER(ConnectionRef) COLLATE Latin1_General_CI_AS,' ','') NOT LIKE '%password=%' AND ... NOT LIKE '%pwd=%'))`. Per the Single Code Path Principle, define ONE canonicalize-then-inspect routine and have both the C# validator and the write path call it (see also M7).

### H2. Section 1.4's two rules conflict and admit secret-bearing AAD strings
Problem: Rule 1 rejects `Password=`/`Pwd=` unless the whole value is a `${...}` ref; rule 2 allows the string if `Authentication=Active Directory*` is present. `Authentication=Active Directory Service Principal;...;Password=clientsecret` and `Authentication=Active Directory Password;...;Password=Secr3t!` both parse and carry a resting secret while satisfying rule 2. The rules have no stated precedence, so an implementer can read rule 2 as a sufficient allow condition. The mental model "Active Directory* means passwordless" is false for those two modes.
Fix: State precedence: rule 1 (reject any non-empty `Password`/`Pwd` on canonicalized input) ALWAYS wins. Only the passwordless AAD modes (Active Directory Default / Managed Identity / Workload Identity, plus `Integrated Security=true`) may be inline. `Active Directory Password` and `Active Directory Service Principal` must be rejected inline and pushed fully behind `${...}`. Validate against the parsed `Authentication` enum value, not an `Active Directory*` prefix string match.

### H3. The "single open site" claim is broken: `InferenceService` is a second resolve-and-open path, entirely missing from the design
Problem: Section 6.7 and section 9 discuss only `FlowRunner.cs` (resolve at line 88 in `RunAsync` and line 286 in `PlanCoreAsync`, both verified). But `C:\Projects\SQLFlowV3\src\SqlFlow.Core\Engine\InferenceService.cs` line 95 independently calls `_secrets.Resolve(request.Connection)` and threads the raw `connectionString` into `_schema.GetTableSchemaAsync`, `_profiler.ProfileAsync`, and `_validator.CheckAsync`. It is the engine behind the CLI `infer`/`validate` commands. If the provider interfaces change to `ResolvedConnection` (section 4.2), `InferenceService` will not compile; if they do not, a raw-string open site survives. The design's "Grounded files read" footer does not list `InferenceService.cs`.
Fix: Add `InferenceService.cs` to the section 9 "Change" list: replace `ISecretResolver _secrets` with `IConnectionResolver`, resolve once in `InferCoreAsync` with the appropriate role, thread the `ResolvedConnection` through the schema/profiler/validator calls, and have those providers open via `IConnectionFactory`. Only then is the single-open-site invariant true.

### H4. Source-by-alias is presented as working but no relational reader, resolution, or wired role exists (sections 1.1, 6.7, 8; enum in 4.1)
Problem: Three independent facts, all verified, make `ConnectionRole.Source` dead and the section 8 `source: type: ado, location: "@AdventureWorksOLTP"` example non-functional today:
- `C:\Projects\SQLFlowV3\src\SqlFlow.Sources` contains only Csv/Xls/Json/Xml/Parquet readers (all file-based); there is no `ado`/relational `ISourceReader`. `FlowRunner.ResolveReader` (line 373-375) throws `"No source reader is registered for source type ..."`, so the example fails at runtime.
- `SourceSpec.Location` is consumed only as a file path: `FileSourceReaderBase.ResolveAsync` (lines 379-425) maps it to `SrcPath`, picks an `IFileStore` via `CanHandle`, and globs. No path runs it through `IConnectionResolver`/`ISecretResolver`. `SourceSpec.Location` is also `string?` while `TargetSpec.Connection` is `required string` (verified in `FlowDefinition.cs`), so the model is not symmetric.
- `FlowRunner` resolves only `flow.Target.Connection` (lines 88, 286). Nothing resolves a source connection or stamps `ApplicationName "SQLFlow Source"`. The `ConnectionRole.Source` enum branch in `Canonicalize` (6.1) has no caller.
Fix: Pick one and state it explicitly. Either (a) scope source-side relational connections OUT of this design (target-only) until an `AdoSourceReader` exists: remove or clearly flag the section 8 `type: ado` example as deferred, drop the "carried by both `TargetSpec.Connection` and `SourceSpec.Location`" claim in 1.1, and note `ConnectionRole.Source` is reserved-not-wired; OR (b) bring the relational reader into scope: add an `AdoSourceReader` that receives an engine-resolved `ResolvedConnection` (resolved once with `ConnectionRole.Source`), document the `ISourceReader` signature change needed to pass it (today `GetColumnsAsync`/`OpenAsync` take only `SourceSpec`), and route its open through the same `IConnectionFactory`. Do not ship the `Source` enum branch with no caller (no-stub principle).

### H5. Layering: split the abstractions by type dependency; section 10's `DbConnection` return reframes but does not fully resolve it
Problem: Verified project graph: `SqlFlow.Core.csproj` references only `Microsoft.Extensions.Logging.Abstractions` and `System.Diagnostics.DiagnosticSource`; `Microsoft.Data.SqlClient` lives only in `SqlFlow.SqlServer.csproj`; `Azure.Identity`/`Azure.Core` only in `SqlFlow.Azure.csproj`. Section 3/4.1/9 claim `SqlFlow.Connections` is "pure, depends only on `SqlFlow.Core`, no SqlClient or Azure dependency," yet it defines `IConnectionFactory.OpenAsync` returning `SqlConnection` and `ITokenCredentialCache.GetSqlTokenAsync` returning `Azure.Core.AccessToken`. As written in sections 3/4.1 that project cannot compile. Section 10 decision 1 changes `OpenAsync` to return `System.Data.Common.DbConnection` (to also carry MySQL), which removes the `SqlConnection` leak from the abstraction, but the body of the design (sections 3, 4.1, 9) still says `SqlConnection` and still places `ITokenCredentialCache` (Azure types) in the pure project.

Additionally, the `DbConnection` choice introduces a NEW unaddressed problem: the SqlServer providers cannot consume a bare `DbConnection`. `SqlBulkLoader.cs` line 21 constructs `new SqlBulkCopy(connection, options, externalTransaction: null)`, which requires a `SqlConnection`; `SqlServerSchemaProvider.cs` uses `new SqlCommand(sql, connection)` and `(SqlTransaction)connection.BeginTransactionAsync()` (verified). So every provider must downcast `(SqlConnection)dbConnection`, and an accidental MySQL connection reaching a SQL Server provider becomes a runtime `InvalidCastException` rather than a compile error.
Fix: Correct sections 3, 4.1, and 9 to match section 10 and split by dependency:
- Keep the pure value types (`ConnectionRef`, `DataSource`, `CredentialProfile`, `DataSourceCapabilities`, `StorageContext`, `ResolvedConnection`, enums), `IConnectionResolver`, and `IDataSourceStore` in `SqlFlow.Connections` (or in `SqlFlow.Core`, see L4) since they touch only Core types.
- Place `IConnectionFactory` where it is consumed. With the `DbConnection` return type it can stay provider-neutral, but specify how a SQL Server provider safely obtains a `SqlConnection`: either keep a SQL-Server-specific factory abstraction returning `SqlConnection` (preferred, honors "do not abstract SQL Server away"), or document the single downcast site and a fail-fast guard. Do not leave it implicit.
- Move `ITokenCredentialCache`/`TokenCredentialCache` (Azure types) into `SqlFlow.Azure`, not `SqlFlow.SqlServer` and not the pure project (see M2). 

### H6. Migration mapping (5.3): SourceType -> Kind mapping is factually wrong and double-counts Synapse
Problem: Section 5.3 maps `SysDataSource.SourceType` with "MSSQL->0, AZDB->1, (Synapse split from IsSynapse)->2, MySQL->3." The legacy extended property (verified, `flw.SysDataSource.sql` line 34) states the ONLY valid `SourceType` values are `MySQL`, `MSSQL`, `AZDB`. There is no `Synapse` source value; Synapse-ness is carried entirely by the separate `IsSynapse` bit (line 11). The mapping invents a source value that does not exist and conflates two independent columns while ALSO keeping `IsSynapse` as a capability flag, so a legacy `AZDB` row with `IsSynapse=1` is ambiguous (Kind=AZDB by `SourceType`, Kind=Synapse by the prose). `SourceType` is also nullable `nvarchar(50)`, so a NULL `SourceType` has no Kind and is unhandled.
Fix: Make `Kind` a faithful 1:1 of the three real values, and either drop `DataSourceKind.Synapse` or define it as a NEW V3 value with an explicit, reconciled rule: `Kind = (SourceType=='AZDB' AND IsSynapse=1) ? Synapse : map(SourceType)`, with `IsSynapse` retained only as the capability so the two can never disagree. Add a row for NULL `SourceType` (reject, or a documented default).

### H7. Migration mapping (5.3): SysAPIKey and SysSourceControlType drop real columns and invent/misattribute others
Problem (verified against `flw.SysAPIKey.sql` and `flw.SysSourceControlType.sql`):
- `SysAPIKey` columns are `ApiKeyID, ServiceType (NOT NULL), ApiKeyAlias, AccessKey, SecretKey (MASKED), ServicePrincipalAlias, KeyVaultSecretName`. Section 5.3 silently omits `ServiceType` and `ServicePrincipalAlias`, and frames `SecretKey` as "replaced by `${keyvault:...}` ref" as if new, when `KeyVaultSecretName` already existed for exactly that.
- `SysSourceControlType` has 13 columns including `AccessTokenSecretName` and `ConsumerSecretName` (the existing locator columns the design claims to be inventing as `*Ref`), plus `ProjectKey, SCAlias, ServicePrincipalAlias, SourceControlType, CreateWrkProjRepo`. Section 5.3 lumps `ConsumerKey` with the dropped secrets, but `ConsumerKey` is NOT masked in the SQL (line 10), so it is not a secret.
Fix: Add rows for `SysAPIKey.ServiceType` (kind discriminator / feature config) and `SysAPIKey.ServicePrincipalAlias` (credential link). State that `SecretKey`/`AccessToken`/`ConsumerSecret` were MASKED and their legacy `*SecretName`/`KeyVaultSecretName` siblings are the locator source the V3 `*Ref` continues, not invents. Move `ConsumerKey` to the non-secret feature-config bucket. Enumerate `ProjectKey, SCAlias, ServicePrincipalAlias, SourceControlType, CreateWrkProjRepo`.

### H8. False masking claim: legacy `ClientSecret` was plaintext, not masked (sections 2.3 line 103, and the 5.3 row)
Problem: Section 2.3 states "Legacy stored `ClientSecret nvarchar(100)` masked with `default()`." Verified `flw.SysServicePrincipal.sql` line 8: `[ClientSecret] [nvarchar](100) ... NULL` with NO `MASKED WITH` clause. The masked columns are elsewhere: `SysDataSource.ConnectionString` (line 7), `SysAPIKey.SecretKey` (line 7), `SysSourceControlType.AccessToken`/`ConsumerSecret` (lines 8, 11). So the most sensitive secret was fully plaintext, visible to any reader, which strengthens the case for dropping it but means the document is wrong about the legacy posture.
Fix: Correct section 2.3 and the 5.3 row: `SysServicePrincipal.ClientSecret` was stored in plaintext with no masking; the masking the original system applied to `SysDataSource.ConnectionString`, `SysAPIKey.SecretKey`, `SysSourceControlType.AccessToken` and `ConsumerSecret` was never applied here. Do not assert masking where the SQL shows none.

### H9. Migration gap: there is no legacy secret-name to derive `ClientSecretRef` from, so SP rows are non-functional until hand-authored
Problem: `SysServicePrincipal` has `KeyVaultName` only, with NO `KeyVaultSecretName`-style column (unlike `SysDataSource` and `SysAPIKey`, which both have an explicit secret-name column). The design introduces `CredentialProfile.ClientSecretRef` as the replacement for the dropped plaintext `ClientSecret`, but there is no legacy column to migrate the locator FROM. Additionally, the `CK_*_NoRestingSecret` constraints will REJECT any legacy `ConnectionString` still containing `Password=`/`Pwd=`, so a raw lift-and-shift insert fails.
Fix: Add an explicit migration prerequisite: (a) each plaintext `ClientSecret` must be manually moved into the named Key Vault under a chosen secret name, then `ClientSecretRef = ${keyvault:<KeyVaultName>/<chosen-name>}`; until done the SP row is non-functional by design (fail-closed), not silently defaulted; specify behavior for NULL vs populated `ClientSecret`. (b) State that the migration must transform connection strings to passwordless/`${...}` form BEFORE insert, because the CHECK constraint rejects resting secrets. (c) For the `SysDataSource.KeyVaultSecretName` fold-in, specify the JOIN: `SysDataSource` has no `KeyVaultName` of its own, so the vault name comes from `SysServicePrincipal.KeyVaultName` resolved via `SysDataSource.ServicePrincipalAlias`; document the NULL-`ServicePrincipalAlias` failure case.

## 3. MEDIUM corrections

### M1. Async resolver/factory over a synchronous secret resolver blocks a thread-pool thread (sections 4.1, 6.6)
Verified: `ISecretResolver.Resolve` and `ISecretProvider.Resolve` are synchronous `string Resolve(...)`; `AzureKeyVaultSecretProvider.Resolve` calls `client.GetSecret(...)` synchronously. The proposed 6.6 rewrite keeps the sync signature and a `Lazy<(string,DateTimeOffset)>` whose factory blocks all concurrent waiters on one synchronous Key Vault read, inside the async `IConnectionResolver.ResolveAsync`. Under the all-singleton DI root (verified) this is a hidden sync-over-async blocking point. Fix: add an async path (`ISecretProvider.ResolveAsync` / `ISecretResolver.ResolveAsync` using `SecretClient.GetSecretAsync`) so the await chain is real end to end, and collapse concurrent misses with `Lazy<Task<string>>` rather than `Lazy<(string,...)>`.

### M2. `TokenCredentialCache` placement forces an undisclosed Azure dependency into `SqlFlow.SqlServer`
Section 9 puts `TokenCredentialCache.cs` in `SqlFlow.SqlServer`, but it builds a `ClientSecretCredential` and returns `Azure.Core.AccessToken` (section 6.3), requiring `Azure.Identity`/`Azure.Core`. `SqlFlow.SqlServer.csproj` has no Azure package (verified) and adding one couples the SQL provider to Azure, undesirable for the on-prem/Integrated path. Fix: place `ITokenCredentialCache`/`TokenCredentialCache` in `SqlFlow.Azure`; `SqlConnectionFactory` depends only on the `ITokenCredentialCache` abstraction (resolved via DI) when building an `InjectedToken` connection. Specify which assembly registers it.

### M3. Sovereign-cloud "reuse the legacy AzureEnvironmentDetector" is not grounded (sections 6.6, 7)
Verified: the legacy file `AzureEnvironmentDetector.cs` actually contains class `CloudEnvironmentDetector` (namespace `SQLFlowCore.Services.CloudResources`), which only distinguishes Azure/AWS/Unknown by env-var presence. It has no sovereign-cloud concept, no authority hosts, and no vault-suffix mapping; a repo search for `usgovcloudapi`/`vault.azure.cn`/`AzureAuthorityHosts` returns nothing. The current V3 `AzureKeyVaultSecretProvider` hardcodes `.vault.azure.net` (line 39, verified). There is nothing to reuse. Fix: drop the "reuse" framing; derive the vault DNS suffix and the SQL token audience from `Azure.Identity` authority configuration or an explicit setting (e.g. `SQLFLOW_AZURE_CLOUD=public|usgov|china`), defaulting to public, with `KeyVaultUriOverride` as the escape hatch. Treat it as net-new code with a test per suffix.

### M4. TTL eviction by unbounded recursion can StackOverflow on misconfiguration (section 6.6)
The 6.6 `Resolve` re-fetches expired entries via `return Resolve(locator)`. With a configurable TTL, a TTL of zero or negative makes `expires <= UtcNow` permanently true and recurses to a crash. Fix: require `_ttl > TimeSpan.Zero` at construction (throw otherwise) and replace the recursive expiry path with an iterative re-add (`GetOrAdd` of a fresh `Lazy`) that runs at most once. Specify the factory-side evict-and-retry (6.3/6.4) as a bounded loop with an explicit attempt counter (max one re-fetch) and a distinct exception after the second failure; cover with a test asserting at most two Key Vault calls and two opens.

### M5. Migration mapping (5.3): four `SysServicePrincipal` columns relocated to an unnamed target
`SubscriptionId`, `ResourceGroup`, `DataFactoryName`, `AutomationAccountName` are "relocate-to-feature-config" with no named destination table or YAML section, so they are effectively dropped with a hand-wave. Same for `SysSourceControlType.*` non-secret columns. Fix: either name the concrete V3 destination, or mark these explicitly DROPPED with the reason "ADF/Automation (and source-control) orchestration is out of scope for the V3 connection registry," so the disposition is auditable.

### M6. `BlobEndpointSuffix` and storage-context fidelity gap (section 3 vs 5.1)
The C# `StorageContext` (section 3) carries three fields (`StorageAccountName`, `BlobContainer`, `BlobEndpointSuffix`) but `flw.CredentialProfile` (5.1) has only the first two, and there is no legacy source for `BlobEndpointSuffix`. Fix: note `BlobEndpointSuffix` is a NEW V3 field (sovereign-cloud support) with no legacy origin, and either add the column to the DDL or document it as runtime-derived from the cloud detector, so the record and the DDL agree.

### M7. Two enforcement points, two heuristics, no shared routine (Single Code Path)
The C# 1.4 validator and the SQL CHECK are independent secret-detection heuristics, both bypassable (H1). The design never states they stay consistent. Fix: define ONE `canonicalize-then-inspect-Password-property` routine in code as the authoritative gate (used by both the resolver inline path and the control-plane write path), and treat the CHECK constraint as defense-in-depth. Also state who may INSERT/UPDATE `flw.DataSource`/`flw.CredentialProfile`: least-privilege (section 7) covers the runtime SELECT-only reader but not the control-plane writer the CHECK is meant to backstop.

### M8. Redaction story does not cover non-connection-string secrets
Section 6.5 redacts only connection text via `SqlConnectionStringBuilder`. But sections 2.3/5.3 fold `SysAPIKey`-style secrets and source-control tokens into the same credential resolver; these are not connection strings, so builder-based redaction does not apply. Fix: add a redaction rule for raw resolved secret values used outside a `SqlConnection` (e.g. REST API keys), and extend the redaction test scope (6.5) to the new `SqlConnectionFactory`/`SqlDataSourceStore` code and to exceptions thrown deeper in `OpenAsync`.

### M9. Uniqueness and NULL skew in `Alias`/bit columns not handled by the migration
Legacy `SysDataSource` has its PK on `DataSourceID` only; `Alias` is nullable `nvarchar(50)` with NO unique constraint, so legacy data may hold duplicate or NULL aliases that violate the new `UQ_DataSource_Alias`. The four bit columns (`SupportsCrossDBRef`, `IsSynapse`, `IsLocal`, `ActivityMonitoring`) are all nullable in legacy, so existing rows can be NULL. Fix: state that the migration dedupes/repairs aliases before insert and applies `COALESCE(col,0)` uniformly to all four bits (not just `ActivityMonitoring`, which the design singled out).

## 4. LOW / nits

- L6. Existing tests/fakes are not in the change list. `ConcurrencyTests.cs` constructs `FlowRunner` with the current 12-arg constructor and defines `FakeSchema`/`FakeLoader`/`FakeIndexManager`/`FakeDesiredIndexManager`/`FakeIncrementalProbe` all on `string connectionString` (verified). - L7. `KeyVaultCacheTests` cannot reference the type under test: `SqlFlow.Core.Tests.csproj` references Core/SqlServer/Sources/Yaml but NOT `SqlFlow.Azure` (verified), and `AzureKeyVaultSecretProvider` lives in `SqlFlow.Azure`. Add the project reference or put those tests in a dedicated `SqlFlow.Azure.Tests` project; note in section 9.

Given the "no secrets in memory dumps" spirit, at least acknowledge the managed-string limitation and minimize lifetime.

## 5. What is verified SOLID (survived the red team)

- The single-pipeline resolver model (one `ConnectionRef`, one `IConnectionResolver`, lightweight/full differ only by which `IDataSourceStore` is plugged in) honors two-modes-one-engine and the Single Code Path Principle. The `@`-sigil grammar (section 1.3) correctly disambiguates aliases from AAD UPNs and `${...}` refs.
- Picking `ConnectionStringAuth` (passwordless AAD in the connection string, SqlClient owns the token) as canonical and confining `InjectedToken`/`AccessToken` to the rare cross-tenant case is the correct pooling-vs-token reconciliation (section 6.2). The "no bespoke per-connection token-TTL layer for SQL" decision is right.
- Canonicalization via `SqlConnectionStringBuilder` (collapsing `Server`/`Data Source`, `Database`/`Initial Catalog`) for a stable pool key (section 6.1) is correct, and is also the right place to enforce secretlessness (see H1).
- The stateless/reentrant factory invariant (cache only immutable artifacts, never a `SqlConnection`; physical reuse from the ADO.NET pool) is sound and matches the existing `FlowRunner` per-run `RunContext` isolation pattern.
- Dropping `ClientSecret`/`SecretKey`/`AccessToken`/`ConsumerSecret` from the control DB and replacing them with `${...}` locator columns, with `ResolvedConnection.ToString()` returning the redacted string as a safety net, is the right secrets-never-rest posture (subject to the masking-claim correction H8 and the enforcement holes H1/H2).
- The resolve-once fix in `FlowRunner` (the real double-resolve at lines 88 and 286 is confirmed) is a genuine and correct bug fix.
- The `ActivityMonitoring` "NULL->0" observation is accurate (it is the one bit with no `DEFAULT 0`); generalizing the COALESCE to all four bits (M9) completes it.
- Capabilities riding into providers via `ResolvedConnection.Capabilities` is the correct channel to make the legacy flags drive code generation, and `IDdlGenerator` is correctly left untouched.
- Section 10 decisions 2 (keep surrogate keys), 3 (per-flow credential override through the same pipeline), and 4 (10-minute KV TTL) are coherent and consistent with the architecture.

## 6. Revised open decisions for the user

1. Source-side relational connections (resolves H4). Either (A) target-only for this cut: remove the `type: ado` example and the `SourceSpec.Location` claims, keep `ConnectionRole.Source` reserved but unwired; or (B) build the `AdoSourceReader` now with the `ISourceReader` signature change to accept an engine-resolved `ResolvedConnection`. Recommendation: (A). It keeps this cut buildable and honestly scoped; the design already admits no relational reader exists, and shipping a dead enum branch violates the no-stub rule.

2. Home of the pure value types (resolves H5/L4). Either (A) a new `SqlFlow.Connections` project referenced by both `SqlFlow.Core` and `SqlFlow.SqlServer`; or (B) define `ResolvedConnection` and the capability/credential value types directly in `SqlFlow.Core`. Recommendation: (B). They have no non-Core dependencies, the provider interfaces that mention them already live in Core, and it avoids an awkward `Core -> Connections` edge. Keep the resolver/store implementations in their own project if desired.

3. Factory return type and SQL-Server type access (refines section 10 decision 1, resolves the H5 downcast gap). Either (A) `IConnectionFactory.OpenAsync` returns `DbConnection` (MySQL-capable) and SqlServer providers downcast to `SqlConnection` at a single guarded site for `SqlBulkCopy`/`SqlCommand`/`SqlTransaction`; or (B) keep a SQL-Server-specific factory abstraction returning `SqlConnection`, with MySQL behind a sibling factory. Recommendation: (A) only if MySQL truly ships in this cut (decision 1), with an explicit fail-fast guard so a wrong-provider connection throws a clear error, not a raw `InvalidCastException`. If MySQL can wait, prefer (B): it honors "do not abstract SQL Server away" and removes the downcast entirely.

4. Async secret read (resolves M1). Either (A) keep `ISecretProvider` synchronous and document the blocking KV read; or (B) add `ResolveAsync` end to end. Recommendation: (B). The resolver and factory are already async and KV is network I/O; under all-singleton DI this removes a real thread-pool blocking point and lets the stampede collapse use `Lazy<Task<string>>`.

5. `ITokenCredentialCache` placement (resolves M2). Either (A) `SqlFlow.SqlServer` (forces an Azure package into the SQL provider); or (B) `SqlFlow.Azure` (already has Azure.Identity/Azure.Core), consumed by the factory via DI abstraction. Recommendation: (B). Keeps the SQL provider Azure-free for the on-prem/Integrated path.

6. Sovereign-cloud suffix source (resolves M3).
